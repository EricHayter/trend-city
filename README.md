# DESCENT

A cel-shaded momentum platformer. One character, one mountain, summit to valley floor
against a clock. Built in Three.js and TypeScript.

The movement is modelled directly on *Spark the Electric Jester 3* — the same speed table,
the same air control, the same dash, wall-run, grind and slide, with the constants
converted out of Spark units into metres (see **Speed and units** below). What the
mountain adds that Spark does not have is a continuous descent, so the one term Spark's
table never needed is the one this game has to supply for itself: a grade-dependent
terminal speed.

**Every asset in this repository is generated by the code in this repository.** No
downloaded models, textures, HDRIs, fonts, or audio. Every mesh is built from geometry
primitives and procedural lathes in code. Every texture is rasterised with canvas 2D or
evaluated in a shader. Every sound is synthesized with the Web Audio API. The mountain is
noise plus a hydraulic erosion simulation. The letterforms in the HUD are drawn as paths.

```bash
npm install
npm run dev
```

That is the whole setup. Open the URL it prints and you are running.

## Controls

| | |
|---|---|
| **W** **A** **S** **D** / arrows | Move. Raw ±1, deliberately unsmoothed — Spark's stick has no ramp and neither does this |
| **Space** | Jump. Tap again in the air to double jump; against a wall it is a wall jump |
| **Shift** | Dash — 1.19× top speed, and the fastest way through a gap |
| **Ctrl** / **C** | Crouch. Held above the slide floor it becomes a slide; on a slope the slide accelerates |
| **K** | Dive — a downward air attack that bounces off what it hits |
| **J** | Attack |
| **F** | Boost — spends the meter |
| **R** | Reset to the last checkpoint |
| **B** | Look back |
| **V** | Cycle camera |
| **Esc** | Pause |
| **`** | Debug overlay |

A standard gamepad works too: **A** jump, **X** attack, **Y** dive, **RB** dash,
**LT** crouch, **RT** boost. The left stick is analogue where the keyboard is not.

Grinding and wall-running have no button. A rail mounts when you cross its line with any
real speed at all, and mounting *grants* you `GRIND.mountFloor` — 7.1 m/s — if you arrived
slower, because a rail should never be the thing that slowed you down. A wall needs 3.8 m/s
into the face and, unlike a rail, needs you **airborne or dashing**: you cannot start a
wall run by walking into a cliff, which is why the chimneys are entered off a jump. The HUD
prints a **RAIL** or **WALL** prompt when either is in reach. Getting off either is a jump,
and a wall jump is additive — it stacks onto whatever vertical you already had, which is
the entire reason a chimney gains height per jump instead of resetting to a fixed rise.

**The one mechanic worth learning:** every grade has a terminal speed, and it is barely
above flat-ground top speed. Pointing yourself down the steepest line gets you to that
terminal *sooner*, but it does not raise it — a 25° face and a 45° face top out 0.5 m/s
apart. The speed above that ceiling only exists in the traversal set: a boost pad is worth
+32% of top speed, a dash ring leaves you at 1.30×, a rail holds whatever you brought onto
it through a corner that would otherwise scrub it off. So the fast line is not the steep
line, it is the line that strings affordances together — which is the whole reason there
is a route decision to make at all. `SLOPE.overTaper` in `src/player/SparkConstants.ts` is
the constant that makes this true and documents the measurements behind it.

## Speed and units

Worth knowing before reading `SparkConstants.ts`, because it explains the shape of the
whole file.

Spark 3's published numbers — gravity 36, top running speed 74 (185 on its HUD) — are in
*Spark units*, and they are only self-consistent with each other. Nothing in them says how
long a Spark unit is. Treating one as one metre gives a character running at 266 km/h
under 3.7 Earth gravities on a mountain built in real metres, which is what the first pass
did, and it broke every system calibrated against it at once: the camera could not hold
its subject, the turning radius was 34 m on a 15 m trail, and par pace was above the
absolute speed ceiling.

Anchoring instead on the one constant with a real value to match — gravity — fixes the
scale: `9.81 / 36 = 0.2725` metres per Spark unit. Top running speed becomes 20.17 m/s,
gravity becomes 9.81 m/s².

The rescale preserves Spark's feel exactly, because it is uniform. Lengths, velocities and
accelerations all carry one factor of that constant and **durations carry none** — a time
`v/a` is unchanged when both `v` and `a` are scaled by the same factor, so every hang time,
coyote window, cooldown and input buffer stays at the number Spark uses, and every arc
keeps its shape at 0.2725 of its size. Angles and turn rates are likewise untouched, which
is what shrinks the turning radius to 9.2 m and hands steering back.

So every number in `SparkConstants.ts` is still *Spark's own number*, wrapped in a
converter: `accel: sparkAccel(36)` is Spark's 36. Read the arguments to compare against the
game; read the exports to get metres. The HUD keeps reading 185 at top speed, because
`SPARK_UNITS_PER_MPS` is derived from the same constant.

The corollary, and the reason it is worth a section: a constant that *restates* a value from
the speed table instead of *reading* it will desync silently. That bug was found in seven
places — a camera reference speed, two speed-line thresholds, five booster powers and a
hardcoded gravity inside a ballistic solve — and all of them now derive from `RUN`, `JUMP`
or `GRAVITY`.

## Art direction

One committed palette: **dawn-gold alpine**. A low sun at 21.5° raking across the mountain
from the east-southeast, cool violet-slate shadows, and a teal-shifted haze stacking the
far ridges into flat paper layers. Every colour in the game is declared in
`src/npr/Palette.ts` and nowhere else.

Three rules the code enforces structurally, not by convention:

1. **There is no PBR to leak in.** There is no `MeshStandardMaterial` anywhere in the
   project and no code path that could construct one. Every surface is a `CelMaterial`
   built from a `RampPreset`.
2. **Shadows are chromatic.** The dark band of every ramp is a hue-rotated, desaturated
   cousin of its lit band pushed toward violet — never a multiply toward black. This is
   the largest single difference between "cel shader" and "cel painting".
3. **Nothing is a gradient.** Lighting, specular, rim, fog, sky, and even the fake
   reflections in the matcaps are quantised into hard bands.

### The NPR pipeline

```
 shadow cascades  →  G-buffer prepass  →  hull outlines  →  main cel pass
                                                                  ↓
   composite  ←  grade (LUT)  ←  bloom  ←  speed lines  ←  Sobel interior lines
```

**Ramp lighting** — 3–4 band gradients with per-material thresholds and band colours.
Rock, dirt, foliage, skin, cloth, anodised aluminium, glass and wet rock each get their
own tuned response rather than one global look. The band edge is anti-aliased by exactly
the screen-space derivative of the shading term, which is what stops the terminator from
crawling when the camera moves — the most common failure of browser toon shaders.

**Two cooperating line systems.**

- *Inverted hulls* on the character, rocks, trees and every traversal affordance. Vertices
  are pushed along **smoothed** normals — every outlined geometry runs through
  `finalizeGeometry()`, which welds positions on a spatial hash and averages the split
  normals at every hard edge. Without that step the hull tears open at every corner of
  every box, which is the gap you see on most browser toon shaders. Width is scaled by
  view distance and projection so a stroke holds `LINES.targetPixels` — 2.15 device px —
  independent of distance, tapering only past 42 m so far objects do not go blobby.
- *Screen-space Sobel* over the MRT normal + depth + material-ID prepass, for the interior
  lines a hull structurally cannot produce: a crease inside a silhouette, an arm crossing
  a torso at the same depth, the boundary between a shoe and the ground.

The two are tuned so they never double up into muddy black — the Sobel pass is suppressed
where the hull already laid ink.

**Variable line weight.** Stroke thickness is modulated by surface curvature (computed per
vertex during the outline weld) and by distance, so lines taper on flats and swell into
creases the way a hand-drawn stroke does. This one detail is most of the difference
between "toon shader" and "drawn".

**Stylised shadow interiors.** Inside shadow bands, a screen-space hatch atlas is blended
in at low opacity — three tiers of real hand-drawn-feeling strokes with per-stroke weight
and bow variation, rotated 34° off the pixel grid, broken up with low-frequency noise. It
darkens toward the shadow hue rather than toward black. It should read as paper tooth, not
as a filter.

**Quantised atmospheric depth.** Distance fog is stepped into four discrete plateaus. Far
ridges snap between them instead of blending, so each one reads as a single flat
silhouette stacking behind the one in front — the classic anime mountain composition.
Continuous fog would dissolve the same ridges into a grey gradient.

Plus: a banded gradient sky dome with hard-edged cel clouds at two parallax depths,
geometric sun shafts built as actual quads (not a radial blur), banded specular with
hard-edged highlight shapes, matcap fake reflections with no cubemap probe anywhere in the
project, Fresnel rim light on the character, a hard-threshold bloom that stays graphic,
and a colour-grading LUT generated in code from the palette's grade constants.

## The mountain

A 2048² heightfield over 4 km of world, built from domain-warped fBm, ridged multifractal
for the crests, and billow for the foothills — then run through a **droplet-based
hydraulic erosion simulation**. Raw noise reads as lumpy and fake; erosion is what puts
real ridgelines, gullies and alluvial fans on a mountain. A thermal-erosion pass settles
the scree slopes to a believable angle of repose afterwards.

The course is not pasted onto the terrain. A soft, wide corridor prior biases the
heightfield toward a continuously descending runnable band *before* erosion runs, so
erosion carves genuine gullies and spurs around the route. The jump lips, the ravine, the
narrowed ridge and the stream channel are carved back in *after* erosion, because erosion
would silt them up and "the jump eroded away" is not a debuggable failure.

Material zones are assigned by altitude, slope and accumulated erosion — grass and
wildflowers low, dirt and exposed rock mid, scree in the gullies, snow at the peak — with
hard cel transitions between zones along an irregular, noise-perturbed boundary.

Rendered as a geometry clipmap: concentric rings of decreasing resolution, snapped to each
ring's texel grid so the terrain does not swim under the camera, morphed between levels so
nothing pops.

## The course

2000 m of route, 638 m down to 100 m — **538 m of descent**, averaging a 27% grade. Nine
sections, with the route distances the track actually reports:

| | | |
|---|---|---|
| 1 | **Technical start** | 0–242 m — exposed rock, tight and off-camber |
| 2 | **Scree run** | 243–621 m — open and straight, build speed on low-grip ground |
| 3 | **Switchbacks** | 621–1135 m — bermed corners through the tree line, tightening |
| 4 | **Rock garden** | 1136–1329 m — a broken diagonal that punishes a bad line |
| 5 | **Tabletop** | 1329–1437 m — a clean, readable lip |
| 6 | **Ravine gap** | 1437–1552 m — a genuine 12 m hole in the ground, with a kicker on the near lip and a dash ring over the middle |
| 7 | **Ridge sprint** | 1552–1801 m — a knife edge with real exposure on both sides |
| 8 | **Stream bed** | 1802–1973 m — a drop-in onto wet rock |
| 9 | **Final sprint** | 1973–2000 m — open run-out to the finish gate |

Checkpoints, split times, wrong-way detection and a corner-preview indicator.

**Par is 74 s and the clock is 185 s.** Par is measured, not guessed: an autopilot that
holds nothing but forward, steers on the route tangent and never touches a rail, a wall, a
dash or a shortcut gets down in 78.5 s. Par sits 4.4 s inside that, so holding one key
does not reach it and the traversal set is what closes the gap. The clock is deliberately
2.5× par — it is a fail-safe, not the challenge, and the thing it catches is a player who
walks (a walk is 245 s).

## Traversal

The descent is not just terrain. Planned per course from the track and the terrain by
`src/traversal/Layout.ts`, as a pure function of the seed — so the same course always has
the same rails in the same places, which is what lets you learn a line and what lets the
capture harness produce comparable frames.

| | |
|---|---|
| **25 rails** | 3.2 km of grind line over a 2 km course, because they overlap as alternatives rather than queueing up. Mounting grants a 7.1 m/s floor and holds momentum through a corner that would otherwise scrub it. All 25 verified mountable, from the ground and dropping in from above |
| **12 wall plates** | 349 m of runnable face, 11–16 m tall. 4 of them are halves of a facing pair — the two wall-jump chimneys, each four to six jumps of climb, where the ascent is the point. All 12 verified runnable |
| **12 boost pads** | Additive, +32% of top speed, capped so a chain of them cannot stack past the boost ceiling |
| **2 springs** | Absolute: replaces your velocity with a fixed launch worth about two of your own jumps. A recovery for a player who ran wide, not an exploit |
| **7 dash rings** | Absolute, 1.24–1.30× top speed along the ring's axis. This is what carries a gap crossing or a shortcut exit |
| **1 kicker** | Deflective: rotates your velocity up by the 24° lip angle at 86% efficiency, keeping the magnitude. Everything you get out of it, you brought — arrive slow and it is a hop, arrive at speed and it is 7.1 m/s of lift, a 2.6 m apex and 1.4 s of air, about 24 m of carry against the ravine's 12 m |
| **692 pickups** | 663 fragments, 11 shards, 7 charges, 6 time bonuses, 5 cells |

Two implementation notes that are load-bearing rather than incidental:

**Every probe is swept, not point-sampled — though no longer for the reason the code used
to give.** All four probe files argued that a point test would *miss* features the player
flew straight through, and miss more of them the faster you go. That was arithmetic on the
old broken speed scale: 0.62 m per step against a 1.5 m pickup reach. A step covers 17 cm
now, `SOLVER.maxSubstep` caps a probe segment at 35 cm regardless, and the tightest
tolerance on the course is 1.5 m — so every window is at least eight steps wide and a point
test would hit all of them. Four comments were arguing from a number none of them read,
which is the same failure as the constants, and all of them now say so. What the sweep is
actually worth: it reports the *closest approach*, which is the point a rail mount snaps to
and the tiebreak when two boosters overlap, and it is a statement about the geometry rather
than about today's speed table. Pickups keep one property the others do not need — they
return every hit in a step, not the nearest, because a launch can put two inside the 1.5 m
reach at once and dropping one would be silent theft.

**Rails, walls and boosters are merged into route chunks; pickups are instanced.** 692
collectibles as individual meshes would be 692 draw calls plus 692 outline hulls, which is
more than the rest of the frame put together — but a collectible has to vanish when taken
and spin while it waits, and neither is expressible on a merged mesh. So the static
affordances merge by route window and the collectibles get one `InstancedMesh` per kind,
five draw calls for the whole course, with the spin, bob and collect pop living in the
instance matrix.


`src/game/Contracts.ts` is the spine. Every subsystem is written against those interfaces
and nothing else, which is what let terrain, physics, the character rig, the traversal set,
the camera and the HUD be built independently without any of them reaching into another's
internals.

### Three engine decisions worth knowing about

**Physics runs at a fixed 120 Hz with an accumulator, and rendering interpolates.** A
variable-step simulation changes its handling when the frame rate changes, which is
unacceptable when the whole game is a movement game. The accumulator is clamped at 6
steps: if the tab is backgrounded for four seconds we drop the backlog rather than running
480 steps in one frame and turning one hitch into a permanent stutter.

**Resolution is governed, not fixed.** A rolling *median* of the last 40 frame times walks
the render scale between bounds — median rather than mean so one GC pause doesn't drag the
resolution down for four seconds. It drops fast, climbs slowly, and has a dead band, so it
never pumps.

**Collision resolves the into-surface velocity on Y only.** Textbook collide-and-slide
projects the whole penetrating velocity out along the surface normal, and on a *descent*
that is an energy pump: the grounded branch sets `velocity.y` from the horizontal speed so
the character follows the surface, the substep lands a few millimetres inside the next
heightfield sample, and projecting that out along the normal converts the vertical the
branch just prescribed back into *horizontal* speed — which the next step's `velocity.y` is
recomputed from, larger. It closes the loop with a little more speed every substep, and it
runs after the speed clamp, so nothing bounds it. Measured: an autopilot holding only
forward hit 113 m/s two seconds past the start line — above the hard ceiling itself — and
stayed pinned there for the remaining 1990 m. The horizontal velocity is already exactly
what the grounded branch decided, so Y is the only axis the resolve has any correction to
make.

## The review harness

```bash
npm run capture:install          # one-time: playwright chromium
node tools/capture/capture.mjs --all
```

Loads the game in headless Chromium (real Metal-backed WebGL on macOS), **takes the
clock**, and steps the simulation manually at a fixed dt. A captured sequence is therefore
identical regardless of how fast the machine renders it — which is the entire point of
having a harness, because otherwise two builds cannot be compared.

Produces:

- retina stills at named poses (`--poses`, `--pose <name>`)
- PNG frame sequences at a fixed timestep (`--seq <name> --frames <n>`)
- **contact sheets** — a labelled grid of a sequence's frames in one image, which is the
  only form in which motion can actually be reviewed
- optional `.webm` clips (`--video`)

Stills judge composition, line work, banding, palette and silhouette. Sequences judge
animation quality, weight, camera feel, and whether speed reads as speed.

Alongside the poses, `tools/capture/` holds single-purpose probes that answer a question
with a number instead of a picture — `_autorun.mjs` drives the whole course on autopilot
and reports per-mode speed attribution and every single-step velocity discontinuity, which
is what found both the energy pump above and the unscaled booster impulses. A pose says how
something looks; a probe says whether it is true.

## Performance

Target: locked 60 fps at retina on an M-series Mac in Chrome, with no frame spikes on
jumps or landings. Not yet verified in a real session — the last measured main pass was
22 ms, and closing that is open work.

- Terrain clipmap with vertex-shader height fetch and inter-level morphing
- All foliage, rocks, dust, debris and collectibles instanced
- Traversal affordances merged into route chunks, drawn through a moving window
- Hard per-chunk frustum culling, distance-scaled instance counts, dithered LOD fades
- Adaptive pixel ratio governor
- The HUD canvas redraws only changed regions rather than the whole retina surface
- Zero allocation in physics, IK and particle update paths — scratch objects at module
  scope

and the current render scale.
